# 微信公众号文章写作

把一个选题写成读者愿意点开、能读完、想收藏或转给具体对象的文章。追求可信、具体、有判断，而不是“像公众号”的腔调。

## 职责边界

- 负责选题、研究、事实、标题、结构、正文、删稿、配图策划和发布衔接。
- 把正文排版、预览和粘贴合规交给本仓库的 `wechat-typeset`；不要手写公众号 HTML。
- 只有用户明确说“发布”“推送草稿箱”等才创建草稿；写完、排版不等于授权发布。

## 不可妥协

- 一篇只服务一类核心读者，只解决一个主问题，只兑现一个主承诺。
- 不编造经历、场景、热度、数据、引用、人物态度或来源。
- 区分事实、官方说法、第三方结论、用户一手材料和作者推断。
- 涉及新闻、价格、产品能力、政策、人物职务等易变事实时，先搜索核查。
- 信息增量高于篇幅和文采。没有新增事实、机制、比较、判断或行动价值的段落，删除。
- 默认写单篇。只有用户要求系列，或一个主承诺确实无法在单篇兑现时，才规划 2–5 篇。

## 去除 AI 味并保留文学性

文学性不是堆形容词，而是让事实、思想和人的处境获得可感知的形状。趣味性不是插段子，而是让读者在意外、节奏和细节中继续读下去。

- 先找到本篇独有的叙事发动机：一个人、一件物、一个动作、一场对话或一个持续变化的问题。不要用抽象概念排队充当结构。
- 让概念从场景中长出来。先让读者看见、听见或做出判断，再命名概念；不连续解释三个以上术语。
- 保留人的声音和不完美：迟疑、误解、改口、细小动作和具体后果比“有人认为”更有生命。不得把虚构场景伪装成真实经历。
- 句子服从呼吸而非模板。长短交替，允许克制的偏锋、停顿和回声；不要让每段都以结论句收口，也不要把相邻句子修成同样长度。
- 幽默从性格、处境和逻辑错位中发生。笑点要同时推进理解；删掉只为显得俏皮的梗、括号吐槽和密集类比。
- 全篇允许一个贯穿性的意象或动作线索，但不反复解释它。意象不能替代事实和因果。
- 观点必须付出代价：写出它排除了什么、牺牲了什么、在哪种情况下会失效。没有阻力的漂亮话通常是伪金句。

AI 腔的完整病症清单（假转折、假金句、排比、抽象词、模板节奏、万能升华、套路标题……）只在 `chinese-human-editor` 一处维护。动笔时心里有数，成稿后按第 7 步统一终审，这里不重复。

完成初稿后做一次朗读检验：遮住标题，随机读三段；若听不出具体题材、作者立场和情绪温度，回到场景与句法层重写，不靠增加形容词补救。

## 先选写作模式

- **新闻/观点**：回答“发生了什么、为什么重要、谁会受影响、现在应如何判断”。
- **科普/解释**：回答“为什么、如何运作、怎样验证”。写前完整读取 `references/popular-science-writing.md`。
- **实用/决策**：回答“该不该做、怎样做、何时不适用”，必须给条件、步骤和停止条件。
- **人物/故事**：用人物选择推动叙事，事实与人物弧线并重；不要把人物写成观点的道具。
- **重写/编辑**：先找标题失配、首屏迟缓、信息重复、证据断层和结尾空转，再重构；不要只做同义替换。

可以混合，但只能有一个主模式。

## 工作流程

### 1. 建立内部选题卡

动笔前写清五句，不机械放进成稿：

- **读者**：谁会点开，他已经知道什么？
- **张力**：哪件事与他的直觉、利益或处境冲突？
- **主张**：全文最终要证明的一句话是什么？
- **回报**：读完后，他能多做出哪个判断、解释或动作？
- **证据**：哪三类材料分别支撑“发生了什么、为什么、会怎样”？

如果主张只能写成“行业正在变化”“值得关注”“因人而异”，继续研究或缩小选题。

### 2. 搜集“最少但足够”的证据

为每个承重结论建立证据记录：原始链接、来源、日期、它支持什么、不能证明什么。

优先级：

1. 官方文件、原始数据、论文、价格页、系统卡、变更日志、当事人原话。
2. 方法透明、条件可比的第三方测试或权威机构解释。
3. 高质量报道，用于时间线、行业背景和多方立场。

不要用固定条数凑材料。证据不足时缩小结论、明确未知或暂缓成稿；不要用更多边缘信息掩盖核心证据缺口。

科技新品额外核查可用地区、入口差异、默认参数、限制、真实计费、评测条件与迁移成本。数字必须说明基线、差值和现实含义。

### 3. 搭建阅读路径

默认使用三段式认知推进，不把它写成模板标题：

1. **看见问题**：用具体矛盾让读者知道“这与我有什么关系”。
2. **理解变化**：用证据和机制修正第一直觉；全文 1/3–2/3 处出现一次真正的认知转折。
3. **形成判断**：给适用边界、代价、选择或行动，而不是口号。

**章节服务内容，不是必需品。** 经验总结、干货、两千字以内的短文，默认不分章节：一段接一段把事实、做法、坑交代清楚，知识密度高本身就有人味。只有长文、几个部分确实各自独立时，才用 3–6 个 `##` 主章节，每节只承担一个核心任务。标题不要预先编号，编号交给排版器按文章类型决定。

### 4. 写好标题与首屏

先写正文，再定标题。给三个真正不同的方向：

1. **判断型**：直接交付最重要的独立判断。
2. **张力型**：呈现反常识、冲突或代价。
3. **收益型**：说明读者能少踩什么坑、看懂什么或做对什么。

标题通常 14–28 个汉字，包含具体对象和清晰变化/后果，只承诺一件事。禁止夸大、假悬念、双重标题和正文无法兑现的情绪。

**标题宁可平实，不要噱头。** 读者对“一件也不知道”“所有人都低估了”这类制造落差的说法已经麻木，看到只会划走。默认选收益型或判断型：直接说这篇讲什么、读完能明白什么。三个方向里有一个读起来像在吊胃口，就不选它。

首屏约 80–180 字，完成三件事：

- 第一两句给具体场景、冲突、证据或不寻常判断。
- 说明这件事为何影响目标读者。
- 暗示阅读回报，但不把全文答案一次说完。

不要从时代背景、自我介绍、定义、客套话或“最近很多人问我”开始。

### 5. 写正文

- 像有经验的人向聪明朋友解释：自然、克制、有态度，不端着。默认语气是**专业、朴实，带一点幽默**：专业靠准确的事实和清楚的机制，朴实是不拔高、不煽情，幽默从材料里的错位来（一句就够，不硬凹）。
- 段落以 1–4 句为主；长短句交替。换段依据意思，不为了“短句感”把一个句子劈碎。
- 每 300–500 字检查一次：是否新增证据、解释、比较、转折或决定？连续停留在背景介绍就压缩。
- 每个抽象词附近给一个具体对象、动作、例子或后果。
- 例子挑对读者有用的：能让他照着做、或者避开一个坑。作者的情绪插曲（被烦到、放弃了）不当论据。
- 比喻只在真实例子和简化模型仍不足时使用；全篇最多一个主比喻，并说明边界。
- 幽默来自事实与直觉的错位，不硬塞网络梗。
- 引语、表格、列表和代码只在它们比普通段落更清楚时使用。
- 结尾控制在全文约 5%–10%：回扣开头，交付判断或余味，不复述全文，不突然拔高。

不要按官方文档顺序复述功能，也不要用多个比喻替代机制。套话、抽象词和空洞抬升留给第 7 步终审统一清。

### 6. 无情删稿

按结构层、段落层、句子层依次删，不设机械比例：

1. 写下每节唯一新增的信息；答不出来就合并或删除。
2. 删除进入主题前的铺垫、重复结论、解释过的术语、无证据抒情和可移植到任何文章的句子。
3. 把三个相近例子留成最有证明力的一个；把“先说结论—展开—再说结论”压成一次。
4. 检查所有小标题是否在推进问题，而非把正文第一句换个说法。
5. 检查标题承诺是否由正文承重证据兑现。
6. 朗读首屏和结尾；任何“像写稿”的句子改成自然人会说的话。
7. 标出所有抽象名词、排比和总结句；连续两处承担相同功能时只留更具体、更有节奏的一处。
8. 检查幽默是否改变理解或推进人物/问题；纯装饰笑点删除。

删后不得损失证据条件、反例、适用边界或必要因果环节。

### 7. 去 AI 腔终审

删稿完成、事实核实之后，完整读取并执行 `chinese-human-editor`（体裁 `article`），把它作为成稿的最后一道编辑：先留原稿，跑扫描，改，再用它的 `drift.py` 确认事实、数字、引文、链接和限定语没有漂移。终审改的是母稿，`*-gzh.md` 从终审后的母稿生成。

### 8. 发布前质量门

全部通过才进入排版：

- **点击契约**：标题准确，正文兑现同一个问题。
- **首屏留人**：前 180 字没有背景绕行，读者知道为何值得继续。
- **信息密度**：随机抽三段，都能指出不可替换的具体信息。
- **因果完整**：关键判断附近有证据或明确推理链，不用语气代替证明。
- **边界诚实**：写清哪些成立、哪些未知、谁不适用。
- **转发理由**：能说出读者会转给哪类人，以及对方能获得什么；不是靠“金句”硬撑。
- **作者辨识度**：至少有一个由证据推出、来源中没有原样写出的独立判断。
- **非模板性**：随机抽三段，能听出具体题材、人的声音和句法变化；不存在可批量套用的三点式骨架。
- **文学与趣味**：至少有一条贯穿全文的叙事或意象线索；幽默来自材料本身，并帮助读者理解而非打断理解。
- **移动端可读**：段落不过度拥挤，列表不过长，章节数量与材料匹配。

未通过时回到结构层修改，不靠形容词润色。

## 文件产物

每篇保存两份 Markdown：

1. `YYYY-MM-DD-简短主题.md`：标题备选、确定标题、完整正文、文末来源小节。小节名按用法定：正文直接引用了其中的事实、数据，叫 `## 信息来源`；只是作为背景参考，叫 `## 信息参考`。
2. `YYYY-MM-DD-简短主题-gzh.md`：一个 `# 最终标题`、正文、精简可点击来源。

`*-gzh.md` 规则：

- 只保留一个 `#`；主章节用 `##`，子章节用 `###`。
- 不在标题中手写 `01/02`；章节编号由 `wechat-typeset` 按文章类型决定。
- 不放标题备选、选题卡、写作说明、系列规划等过程内容。
- 不写内联 CSS 或公众号 HTML。
- 图片使用相对路径：`![具体说明](_images/topic/image.png)`。
- 代码、命令和 Prompt 使用围栏代码块。

如果用户只要求文案或母稿，可以到此结束；如果要求完整公众号成品或排版，继续读取并使用 `wechat-typeset`。

## 配图与封面

- **每篇默认都要有原创封面**，不能用脚本自动生成的纯色标题封面交差。正文插图按内容需要：机制、结构、对比讲不清时才配，不为“图文并茂”凑图。
- **配色跟着内容走**，不套固定色板：先从文章的题材和情绪定两三种主色，封面、插图、排版的点缀色（wechat-typeset 的 `--accent`）用同一套，彼此协调。
- 有生图工具就用它出封面和意象图；没有时用代码画（SVG / Canvas 写成 HTML，headless Chrome 截图），源文件放在 `_images/<主题>/src/`，方便以后改。
- 抽象观点和核心隐喻优先原创生成；新闻现场、产品界面、人物照片优先真实来源。
- 封面默认无标题，宽幅、主体单一，缩略图尺寸仍能看懂。
- 图片放在 `_images/<简短主题>/`，正文用相对路径。
- 不让生图模型生成大段中文、品牌 Logo、精细产品界面或可读小字。

## 排版与发布

排版必须使用 `wechat-typeset` 的脚本（排版、校验、预览），交付正文 HTML 与预览页。不要复用旧 HTML 或手写样式。

只有用户明确授权发布时，才运行：

```bash
python3 <本skill目录>/scripts/publish_to_wechat.py \
  "<母稿或gzh输入稿.md>" \
  --content-html "<wechat-typeset 生成的 *-排版.html>"
```

追加封面（每篇都应有原创封面）：

```bash
--cover "<封面图路径>" --cover-no-title
```

摘要自己写，用 `--digest` 传入：120 字以内，一两句说清这篇讲什么、读者能得到什么，不要让脚本截正文开头（截出来往往停在半句）。

草稿已经建过、只是改了正文或封面，用 `--update <草稿 media_id>` 原地更新，不要再建一篇重复草稿。

发布前确保 HTML 校验通过、图片可上传、封面可用。发布配置从当前目录或本 skill 目录的 `.env` 读取 `WECHAT_APP_ID`、`WECHAT_APP_SECRET`，可选 `WECHAT_AUTHOR`；`.env` 只由用户自己填写，不要提交到任何仓库，也不要在回复里复述其中的值。脚本默认在本 skill 的同级目录 `wechat-typeset/` 找校验和预览脚本，装在别处时设环境变量 `WECHAT_TYPESET_HOME`。

## 完成时告知用户

说明母稿、gzh 输入稿、干净正文 HTML、预览页、校验结果；若已发布，再给草稿 `media_id`。不要用“你觉得怎么样”结束交付。
