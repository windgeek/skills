# Skill 精炼

skill 是越用越长的：每次踩坑、每次用户纠正，都会往里加一条。只往后追加，几轮之后就会出现三种病：

- **重复**：同一条规则在两三个地方各写一遍，措辞还略有不同；
- **冲突**：新规则推翻了旧规则，旧的却还留着（“每句不超过 20 字”和“长短句交错”同时存在）；
- **堆积**：规则按时间排，而不是按主题排，SKILL.md 越来越长，真正要紧的硬规则被埋在里面。

这三种病的后果是一样的：agent 读到互相打架的指令，随机挑一条执行，用户说过的话又被违反一次。所以**每次改完 skill，都要做一遍精炼**，不要等它乱了再大扫除。

## 什么时候做

- 刚把一条新经验、一次用户反馈写进了某个 skill（最常见）；
- 用户说“总结到 skill 里”“更新一下 skill”“skill 有点乱”；
- 一个 skill 依赖另一个 skill，改了其中一个（冲突常常跨 skill 出现）。

改动很小（修一个错字、改一个路径）时，只跑第 3 步的脚本即可。

## 流程

### 1. 先通读，再动笔

把这个 skill 的 SKILL.md、references/ 下的文件、scripts 的用法说明**全部读一遍**；它依赖或被它依赖的 skill，读和这次改动相关的部分。不通读就追加，是重复和冲突的根源。

### 2. 给新内容找归属

新规则不是“加一条”，而是“放进去”：

1. **已经有一条在讲这件事吗？** 有：把新的案例、新的边界补进那一条，必要时改写它，不另起一条。
2. **没有：它属于哪个主题？** 放进对应的小节。没有合适的小节，而同类规则已经有三条以上，就新建一个小节，把它们一起搬进去。
3. **它推翻了旧规则吗？** 推翻就改掉旧的，不要两条并存。按用户**最新**的意思统一；拿不准哪个是用户现在要的，就问。
4. **它在别的 skill 里也有吗？** 只在一处写全（通常是更通用的那个 skill），另一处写一句指针（“见 X 的 Y 节”）加上本处特有的补充。

### 3. 跑体检脚本

```bash
python3 <本skill目录>/scripts/lint_skill.py <被改的skill目录> --related <相关skill目录> ...
```

它只读不写，会列出四类线索：

| 类别 | 查什么 |
|---|---|
| 结构 | frontmatter、SKILL.md 篇幅（默认超过 500 行或 20 KB 报）、断链、没被任何文件提到的 references 文件 |
| 冲突? | 同一话题出现不同的数字（“10–20 段”和“20–40 段”）；“必须 / 不要”说法相反、话题相近的条目 |
| 重复 | 跨文件、跨 skill 几乎一样的条目 |
| 堆积 | 一个列表平铺十几条；日期 / 版本戳很密而小标题很少（按时间追加的迹象） |

脚本报的是**线索**，逐条回到上下文判断：真重复就合并，真冲突就统一，误报就放过。

### 4. 分层：SKILL.md 只放该常驻的东西

SKILL.md 每次触发都会整份读进上下文，越短越好。它只放：

- 触发条件和总流程；
- 硬规则（违反了用户会直接指出的那些），每条一两句；
- 指向 references/ 的指针，并说明什么时候去读哪个文件。

案例、长解释、历次教训的来龙去脉，放进 references/，按主题分组，文末给一份“自查顺序”。能让机器查的规则，优先写成 scripts 里的检查，这比多一条文字规则可靠。

### 5. 精炼时不能丢的东西

- **用户的要求一条都不能弱化。** 合并时措辞可以变短，意思不能变软；“不删减”不能精炼成“尽量少删”。
- **证据要留。** 每条规则保留一个最能说明问题的案例或用户原话（压缩到一两句），读的人才知道这条规则为什么存在、边界在哪里。出处戳（日期、版本、期号）可以留在括号里，但不要按戳排序。
- **做对的事也要留。** 有证据的“有效做法”和教训同等重要，合并时不要只剩禁令。
- **拿不准就问。** 两条规则看似冲突、又都像是用户的意思时，不要自己裁决，把两条原文摆给用户选。

### 6. 收尾报告

改完再跑一次第 3 步的脚本，然后用几句话告诉用户：

- 新内容放到了哪里（合并进哪一条 / 新建了哪个小节）；
- 合并了哪些重复，统一了哪些冲突（旧说法 → 新说法）；
- 挪到 references/ 的内容，以及 SKILL.md 的篇幅变化；
- 脚本还剩哪些线索、为什么保留。

不要只说“已优化”。用户要能从报告里看出这次改动没有丢掉他说过的任何一句话。

## 自动提醒（可选，需用户同意后安装）

本 skill 的 description 已经让 agent 在改完 skill 后自己想起来用它。想要更可靠的提醒，可以在支持钩子的 agent 里，让“写入 skill 目录下的文件”这个动作触发一次提醒。`scripts/remind_hook.py` 是给 Claude Code 写的 PostToolUse 钩子：同一个会话里，每个被改动的 skill 只提醒一次，并附上该 skill 的体检命令。

安装它要改 agent 的设置文件，属于会改变用户本机配置的操作：**先征得用户同意**，说明会改哪个文件、怎么撤销。Claude Code 的配置示例：

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Write|Edit|MultiEdit",
        "hooks": [{ "type": "command", "command": "python3 <本skill目录>/scripts/remind_hook.py" }]
      }
    ]
  }
}
```
