# 知识放在哪里

同时用几个 agent（Claude Code、Codex、Gemini CLI……）时，每个 agent 都有自己的“记忆”。Claude Code 的自动记忆存在 `~/.claude/projects/<项目>/memory/`，只有 Claude 能读；换一个 agent 接手，那些规则等于不存在。所以：

**一条知识只写一处，而且写在所有 agent 都读得到的地方。私有记忆只留指针。**

## 五个位置

| 位置 | 谁读得到 | 放什么 |
|---|---|---|
| 全局约定：一份真文件，各 agent 的全局说明文件软链接到它（例如 `~/.claude/CLAUDE.md` 为真文件，`~/.codex/AGENTS.md`、`~/.gemini/GEMINI.md` 指向它） | 所有 agent，所有项目，每次会话自动加载 | 跨项目的个人习惯：语言、提交信息、shell 的坑、提问方式、善后、关于用户的基本信息。每条一两行，整份控制在一屏左右 |
| skill：一个共享目录（例如 `~/.agents/skills/<名>/`），各 agent 的 skill 目录软链接到它 | 所有支持 skill 的 agent，跨项目 | 怎么做某一类事：流程、标准、技法、踩过的坑和证据。项目无关的部分 |
| 项目 `AGENTS.md`（`CLAUDE.md`、`GEMINI.md` 软链接到它，只有一份真文件） | 在这个项目里工作的所有 agent，自动加载 | 这个项目是什么、目录、命令、当前状态、做过的决定和理由、已查清的“非问题”、只属于这个项目的规则 |
| 项目文档：`docs/`、`DECISIONS.md`、发版记录等 | 按 AGENTS.md 的指引去读 | 长内容：设计、发版细节、测量数据、交接记录。AGENTS.md 只放一行指过去 |
| 某个 agent 的私有记忆 | 只有那个 agent | 只放那个 agent 自己才有的东西（它的权限设置、界面细节），以及一行“规则在哪里”的指针 |

各 agent 读哪个文件名、skill 放在哪个目录，以它们各自的文档为准；原则是只保留一份真文件，其余用软链接。

## 写之前先判断

按顺序问，第一个“是”就是答案：

1. **换个项目也成立吗？** 是个人习惯 → 全局约定；是一类工作的做法 → 对应的 skill（没有合适的 skill，先问用户要不要新建，别塞进不相干的 skill）。
2. **只对这个项目成立？** 当前状态、决定、项目专属规则 → 项目 AGENTS.md；超过十来行的细节 → 项目文档，AGENTS.md 留一行指针。
3. **几个项目共用，但不是所有项目？**（比如同一个系列的几个 App）→ 为这个系列建一个 skill，各项目的 AGENTS.md 写“先读某某 skill”。
4. **只有当前这个 agent 用得上？** → 它的私有记忆。这种情况很少。

agent 的系统提示可能会要求把用户反馈“存进记忆”。照做的方式是：把正文写进上面判断出的共享位置，记忆里最多加一行指针（例如“列提纲的规则在 writing-workflow skill 第 2 步”），或者什么都不加——项目 AGENTS.md 本来就会自动加载。

## 写法

- **写现状，不写流水账**。状态类内容（版本进度、正在做什么）直接改成最新的样子，旧的交给 git 历史；不要“某日补充……某日又补充……”一路往下堆。
- **决定要带理由和日期**：“2026-03-02 决定不换数据库：现在的规模用 SQLite 足够，迁移成本远大于收益”。理由让后来的 agent 知道什么情况下可以重新讨论。
- **查清的非问题要写下来，并写复查条件**：“London 用 Heathrow 坐标是故意的；只有重新比对显示 City 机场更准时才改”。否则每个新会话都会再查一遍。
- **规则写进 skill 后，整理一遍**：合并重复、消除前后冲突（有 `skill-refine` 就用它）。
- **私密信息**：密钥、密码永远不写进这些文件，只写“在哪里”。仓库是公开的或准备开源时，私人内容（IP、账号、家庭网络）放进被 gitignore 的 `private/`，AGENTS.md 写一句“私人信息见 private/，不进 git”。
- **一处改，处处准**：发现两处写了同一件事，删掉一处，留指针；发现互相矛盾，按用户最新的说法统一。

## 新项目

开一个新项目时：

1. 建 `AGENTS.md`（项目是什么、目录、常用命令、当前状态、“开工前先读”），再 `ln -s AGENTS.md CLAUDE.md`（用 Gemini CLI 的再加 `GEMINI.md`）；
2. 项目要用的 skill 在 AGENTS.md 里点名；
3. 项目专属的规则写在 AGENTS.md，不要在项目里建只有某个 agent 认的 skill 目录（如 `.claude/skills/`）——那样只有一部分 agent 看得见。

## 定期梳理（用户说“整理一下记忆 / 梳理各项目”时）

1. **备份**：先把所有记忆文件复制到一个归档目录（例如 `~/.agents/archive/<agent>-memory-<日期>/`），之后的删除才可逆。
2. **盘点**：Claude Code 的记忆可以用 `python3 scripts/inventory.py`（本 skill 自带）列出每个记忆目录对应的项目、项目里有没有 AGENTS.md / CLAUDE.md、每条记忆的类型和大小；目录已不存在的（项目搬走、改名、删除）会标出来。其他 agent 的记忆按它们各自的存放位置手动列。
3. **逐条归类**，每条记忆只有四种去向：
   - 共享位置里已经有 → 删掉记忆；
   - 共享位置里没有 → 按“写之前先判断”搬过去，改写成现状，再删记忆；
   - 已经过期（项目停了、决定被推翻、旧路径）或本身就写错了 → 删掉，不必修好再搬；有保留价值的历史写进项目文档；
   - 项目已不存在 → 先找它搬到了哪里（同名目录、git remote），找到就并进新项目，找不到就只留在备份里。
4. **项目搬家留下的旧记忆**（同一个项目在两个路径下各有一份）：逐条比对，以新路径为准，旧目录清空。
5. **全局约定**：确认各 agent 的全局说明文件仍是软链接（工具升级可能把它换回普通文件）。
6. **记忆目录收尾**：每个项目的记忆索引（Claude Code 是 `MEMORY.md`）只剩指针，或者删空。
7. **报告**：列一张表——每条记忆搬到了哪里、删了哪些、哪些因为拿不准留给用户定。新建或改动的 AGENTS.md 在 git 仓库里时，不要替用户提交，告诉用户哪些文件改了。

## 为什么不靠记忆

- 私有记忆只有一个 agent 读得到。一个项目里 Claude 做设计、Codex 写代码，规则只写在 Claude 的记忆里，Codex 就会照旧犯同样的错；写在 AGENTS.md 才两边都有用。
- 记忆和 skill 各存一份，规则一改只改了一处，两份就开始互相矛盾。
- 记忆按项目路径存放。项目搬家、改名后，新路径下的会话读不到旧路径下的记忆，几十条规则就这样悄悄失联。
